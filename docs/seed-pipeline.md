# 示例数据播种链路分步说明

这条链路解决三件事：样例不再逐条手贴、字段/状态清单一处改处处跟、重置只动被重置的模块。
四个环节各管一段，职责如下。

## 环节总览

```
seed-plan.ts ──加载+校验──▶ seed-definition.ts ──分批──▶ seeder.ts ──按模块写──▶ local-store.ts
（静态计划）                （派生样例行）              （幂等/续跑）            （每模块一键）
                                                                    │
                                              resetModule(模块) ────┘ 只重建该模块
```

## 第 1 步 · 种子定义（管「样例长什么样」）

- `src/data/seed-plan.ts`：唯一需要手工维护的部分。每个模块只声明：编号前缀、
  样例条数（默认 3）、状态轮换（默认取状态清单前 3 个）、基准日期（默认 2026-09-01）、
  少数字段定制值（如延误模块的航班号、影响旅客数）。
- `src/data/seed-definition.ts`：派生器。字段清单、状态清单一律从 `modules.ts` 读，
  运行时生成样例行：编号字段 → `前缀-000N`，日期类字段（名字含 时间/日期/时段）→
  基准日期逐天偏移，定制字段 → 按序号循环取值，其余 → `模块名样例N`。
- **字段或状态清单变了**：只改 `modules.ts`，样例自动跟随，不用动种子文件。
  若计划里的定制值/状态轮换引用了被删掉的字段或状态，`loadSeedDefinition()` 校验
  直接报错（`SeedDefinitionError`），提示同步维护 seed-plan，而不是静默生成脏数据。
- **新增统计维度**：指标来自状态统计，状态轮换自动覆盖新状态，样例随之覆盖，
  不需要再造一批数据。
- 种子定义通过动态 `import()` 异步获取：加载失败（如发版后旧页面取不到新 chunk）
  或校验不过都按失败处理，允许重试。

## 第 2 步 · 播种时机（管「什么时候写」）

- 应用启动时（`main.ts`）执行 `ensureSeeded()`，完成或失败都照常挂载页面。
- 失败时看板页（`Dashboard.vue`）显示失败原因和「点击重试」，重试就是再跑一次
  `ensureSeeded()`——它是幂等的，重复跑安全。
- 读取路径（`listRows` 等）不再隐式播种，读不到就是空列表，播种只走启动流程。

## 第 3 步 · 持久化层（管「落在哪、什么粒度」）

- `src/data/local-store.ts`：每个模块一个 localStorage 键
  `airport-ground-ops:entries:<模块key>`。单模块的读写、损坏、重置都不波及其他模块；
  某个模块的数据解析失败只按空列表处理该模块，不回退种子、不牵连邻居。
- 启动时 `migrateLegacyStorage()` 把旧版全量单键 `airport-ground-ops:entries`
  拆分到每模块一键：目标键已存在时不覆盖（本地优先），全部拆完才删旧键；
  旧键解析失败则保留原键、下次启动再试。

## 第 4 步 · 重置入口（管「回到样例」的爆炸半径）

- `local-service.ts` 的 `resetModule(key)` → `seeder.ts` 的 `resetModuleRows(key)`：
  用最新种子定义重建**这一个模块**的存储键，其他模块的本地记录保持不动。
- 延误处置页提供「重建延误示例数据」按钮作为入口；取不到种子定义会报错并可重试。
- 不要再通过「清掉整个 localStorage 键」来重置——那是旧版单键时代的做法。

## 横切机制

### 幂等（可重复执行）

- 业务编号（如 `DELA-0001`）由「前缀 + 序号」确定性生成，重复跑得到同样的编号。
- 每批播种前按业务编号去重：本地已有的编号一律跳过，id 接续现有最大值分配。
  重复执行不产生重复记录，也不产生重复编号。
- 双保险：journal 记录已完成批次会跳过；即使 journal 丢失，编号去重也保证不重复。

### 断点续跑

- 播种按模块分批，每批写完立即落 journal（`airport-ground-ops:seed-journal`）。
- 中途断了（页面关闭、单批写失败）：下次启动读 journal，已完成的批次跳过，
  从失败/未跑的批次接着补。
- 种子定义版本号（`SEED_PLAN_VERSION`）升版后全部批次重跑一遍，靠去重保证幂等。

### 失败与重试

- 取不到种子定义（加载失败/校验不过）→ 本次播种按失败处理，看板页可重试。
- 单批失败（如存储配额满）→ 记入 journal 并继续后续批次，报告里列出失败模块，
  重试时只补这些批次。

## 两项裁决（依据）

1. **种子定义与本地已有数据冲突时，本地优先。** 播种只补本地还没有的编号，
   绝不覆盖已有记录。依据：localStorage 里是用户真实操作的结果，种子只是冷启动
   的占位样例；让种子覆盖本地等于丢数据，正是这条链路要修掉的问题。
2. **不按上报时间回填存量记录。** 上报时间是业务事实，回填等于伪造用户数据；
   存量记录缺失的新字段由展示层兜底（列表 `?? '—'`、导出 `?? ''`），种子行始终
   按最新字段清单生成。若未来运营上要统一口径，应做一次性显式迁移，
   而不是混进每次启动都会跑的播种链路。

## 维护指引

| 变更 | 改哪里 |
| --- | --- |
| 加/删/改字段、状态、动作、指标 | 只改 `src/data/modules.ts`，样例自动跟随 |
| 改某模块样例条数、编号前缀、状态轮换、基准日期 | `src/data/seed-plan.ts` 对应条目 |
| 给某模块字段定制样例值（如延误原因） | `src/data/seed-plan.ts` 的 `fieldValues` |
| 让全量样例按新定义重建一次 | `SEED_PLAN_VERSION` +1 |
| 删了某字段/状态后播种报错 | 按报错提示同步清理 `seed-plan.ts` 里的引用 |
